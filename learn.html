A CODERABBIT WORKSHOP / ABOUT 30–45 MINUTES

A little world.
Your next good idea.

You have a working game. Now use CodeRabbit to plan a small improvement, build it, and review the change before it ships.

The game and this guide work offline. Account setup, repository hosting, planning, and pull request reviews happen online in GitHub and CodeRabbit. Nothing on this page connects to your account or sends your code.

Bring a GitHub account, this project folder, a browser, and a text editor. A coding agent is optional. No Node, package manager, or local server is needed to run or edit the game.

If you came here from a running game, return to that tab to resume. “Play the game” above starts a fresh page.

FIELD NOTE 01 / YOUR STARTING POINT

Create your CodeRabbit account.

  1. If you do not have one, create a GitHub account first.
  2. Visit the CodeRabbit app and choose GitHub to sign in. Follow the authorization prompts to create or access your CodeRabbit account.
  3. Use a repository you own for this workshop. An organization repository may require its owner's approval to install the app or grant access.
Signing in and connecting a repository are separate steps. Complete both before asking CodeRabbit to work on an issue.

Reference: CodeRabbit quickstart.

FIELD NOTE 02 / GIVE THE RABBIT CONTEXT

Connect this little world.

  1. On GitHub, create a repository named the-burrow-flash. Pick public or private to suit your workshop. Never upload secrets.
  2. Use Add file → Upload files to upload the contents of this folder. Put index.html, learn.html, style.css, and the js directory at the repository root. Include the remaining documentation and test files. Commit the upload to the default branch.
  3. In CodeRabbit, add repositories and follow the GitHub app installation flow. Choose your personal account or the intended organization, then grant access to this repository.
  4. Return to CodeRabbit and confirm the repository is listed. If it is missing, check the selected GitHub account, app installation's repository selection, and any pending organization approval.
  5. Confirm CodeRabbit planning is enabled for this repository before the next exercise. Feature availability and limits depend on your account; check the current app rather than assuming a trial or unlimited usage.

The included hidden .github/ISSUE_TEMPLATE/feature.md is an optional reusable template. If your file picker hides it, copy its contents into that path using GitHub's file editor. You can also paste the issue below without installing the template.

References: GitHub setup and permissions · Planning on GitHub.

FIELD NOTE 03 / A SMALL, TESTABLE CHANGE

Give your idea a finish line.

The adventure intentionally has no collectible carrot counter. Add one as your first feature. Create a GitHub issue in your new repository using this brief:

ISSUE TITLE + BODY 
Title: Add a collectible carrot counter

Goal
Give players a small exploration reward by placing five collectible carrots in the lantern camp.

Requirements
- Put five carrots on reachable floor, away from walls, NPCs, the lantern, and the exit.
- Collect a carrot once when the player touches it.
- Show a readable “Carrots: N / 5” counter in the HUD.
- Retain collected carrots when moving between rooms or returning after death.
- Reset the collection when starting a new adventure or reloading the page.
- Keep the existing controls and key/boss progression working.
- Keep everything local: no dependencies, CDN, fetch, or build step.

Acceptance criteria
- A fresh game shows 0 / 5; collecting all five shows 5 / 5.
- Standing on a collected carrot never counts it twice.
- Leaving and re-entering camp does not respawn collected carrots.
- Death preserves the count; Restart adventure resets it.
- Carrots cannot spawn inside obstacles.
- The HUD stays readable at laptop size.
- The game still runs by double-clicking index.html offline.
- Add relevant checks to the existing browser test page.

Out of scope
Inventory menus, shops, new levels, online leaderboards, and saved games.

Specific behavior makes the plan easier to evaluate. “Make it more fun” leaves too many decisions open. “Five reachable carrots, collected once, reset on restart” gives you something concrete to test.

FIELD NOTE 04 / THINK BEFORE YOU PATCH

Plan with CodeRabbit, in the issue.

Add this comment to your GitHub issue:

ISSUE COMMENT 
@coderabbitai plan

CodeRabbit posts the generated coding plan as an issue comment. When Issue Enrichment is enabled, a Create Plan checkbox can also appear in its comment on a new issue. The command above is the workshop's default route.

Read the proposed files, tasks, and tests. Does the plan keep the game offline? Does it handle death and restart differently? Does it preserve your working adventure? Reply with a refinement:

EXAMPLE REFINEMENT 
@coderabbitai Please refine this plan to keep the game dependency-free and compatible with file://. Explain where the carrot state should live so it survives room changes and death but resets on a new run. Include checks for duplicate collection and unreachable carrot positions. Keep the patch limited to this feature.

Discuss the plan until the steps match your intent. Repeating @coderabbitai plan regenerates it from scratch. Once ready, copy the plan's agent prompts into your coding agent, or follow the tasks manually. Generating a plan does not mean the feature has been implemented.

No response? Confirm the issue belongs to the connected repository, planning is enabled, app permissions are current, and your account has access to the feature. Check the app for limits or errors. Avoid repeatedly posting commands while a request is pending.

Reference: GitHub planning, refinement, and agent handoff.

FIELD NOTE 05 / CLOSE THE LOOP

Build it. Play it. Review it.

  1. Create a feature branch, such as feature/carrot-counter, in GitHub or your Git client. Apply the agreed plan with your editor or coding agent.
  2. Open index.html locally, try the feature, then open tests.html. Test all the issue's acceptance criteria, including death and restart.
  3. Commit your changes to the feature branch and open a pull request against the default branch. GitHub's web editor can make branch commits without installing Git. For edits made on GitHub, download the feature branch ZIP and test that exact version locally.
  4. Describe the behavior, what you tested, and any limitations. Link the issue using Closes #123, replacing 123 with your actual issue number.
  5. Read CodeRabbit's review. Reproduce reported problems, ask for clarification when needed, and fix valid findings. If automatic review is disabled, check the repository settings or request a review with the command below.
  6. Test the revised code. Compare the final result against the issue before deciding to merge. A bot review is useful evidence, not a substitute for playing your game.
PULL REQUEST COMMENT 
@coderabbitai review
ASK ABOUT A FINDING 
@coderabbitai Can you show the sequence of player actions that triggers this problem, and explain how the proposed fix preserves offline play?

References: First code review · Review commands.

BEFORE THE ROOM FILLS UP

Make the demo feel easy.

Suggested flow: 5 minutes to play, 5 to connect the repo, 10 to write and refine the issue plan, then 15–25 to implement, test, and discuss the review. Service response time and implementation time vary.

Keep the story simple: “We already have a working game. We're making one small change. The issue defines success, the plan gives us a path, and the review helps us check our work.”

For later sessions, try another NPC conversation, a new enemy pattern, or a second optional room. Keep each addition in its own issue.
